## 권위 루트와 고정 순서

1. 아스트라가 별도 **Approved** 선행 계약에서 서명 방식·정확 계약 SHA·검증기 허용 경로·신뢰할 승인 기록의 위치와 검증 주체를 먼저 정한다. 이때 아직 만들지 않은 공개키 지문을 꾸며 넣지 않는다. 키 생성·검증 소스 동결 뒤 별도 아스트라 승인 기록이 실제 공개키 지문과 검증 소스 SHA를 고정한다. 임의 로컬 파일이나 caller가 준 `ApprovedSha`를 신뢰 루트로 삼지 않는다. 아스트라가 직접 확인한 승인 기록/개정의 정확 SHA를 외부 검증 호출에 독립 고정한다. 기록에는 권위자, 대상 `CurrentPublicationCleanClone`만 허용한다는 범위, 키 생성·서명 의식의 실제 참여가 남는다. 서명은 이 기록에 결속된 키로 생성됐다는 증거이지 파일 의존 폐쇄·게임 회귀·게시 승인 자체가 아니다.
2. 승인된 단명 서명 세션에서 RSA 3072비트 키를 만든다. 공개 `RSAParameters.Modulus` 384바이트와 `Exponent` `01 00 01`만 새 QA 검증 소스에 고정한다. 공개키 지문은 ASCII·LF·BOM 없는 `AGM-RSA-PUB-V1\nModulus=<표준 Base64>\nExponent=AQAB\n`의 SHA-256으로 정하고 양쪽에서 재계산한다. 개인 지수·소수·키 파일·PEM·명령행·표준출력·로그·원격에는 쓰지 않는다. 개인키는 그 **한 서명 프로세스의 메모리**에만 두고, 최종 소스 동결→계획/manifest 생성→아스트라의 정확 계획 검토→서명까지 동일 생존 세션에서 진행한다. 실패·연결 끊김·재시작 시 개인키 복구를 시도하지 않고 해당 공개키/검증 소스/계획을 폐기한 뒤 새 계약상 절차로 처음부터 동결한다. 장시간 에이전트 대화 메모리나 메시지에 개인키를 보관할 수 없으며, 이 제한 때문에 무인 재개·서명은 허용하지 않는다. 실제 사용 런타임이 비영속 키와 비출력을 보장하는지 승인 전 확인하지 못하면 여기서 중단한다.
3. 검증기는 공개키가 들어간 **최종 바이트**부터 동결한다. 아스트라는 별도 신뢰 승인 기록에 공개키 지문·검증 소스 SHA를 고정한다. 그 다음 현재 Q0/감사/fixture 및 QA 소스가 끝난 뒤 source manifest·input/선택/행·계획을 발급한다. 계획은 해당 승인 기록 SHA와 최종 검증기 SHA, 정확 복제 루트/HEAD/tree/파일 핀·출력 위치·실행 식별자를 참조한다. 검증 소스는 미래 계획·manifest·루나 문서 SHA를 하드코딩하지 않으므로 역참조가 없다. 계획 발급 뒤 아스트라가 실제 원시 계획 SHA와 승인 기록/현재 문맥/nonce를 확인해 **분리된 승인 레코드**에 한 번 서명한다. 루나는 그 후 동결 소스·계획·서명 검증 결과를 독립 검수하고, 아스트라의 마지막 수용 문서만 루나 보고 SHA를 결속한다. 승인 레코드가 미래 루나 SHA를 미리 요구하면 발급을 중단한다.
4. 검증기가 가진 공개키의 신뢰는 단지 파일 안에 있다는 사실에서 나오지 않는다. 외부의 **이미 인증된 Approved 기록**이 공개키 지문과 검증 소스 SHA를 정확 고정해야 한다. 임의 새 키를 넣은 다른 소스·승인 파일·계획 세트를 caller가 제시하면, 이 외부 고정 지문과 불일치해 거절한다. 만약 운영 경로에서 Approved 기록의 실제 SHA/개정을 독립 인증할 수 없다면 서명 검사만으로 아스트라 승인이라고 주장할 수 없으므로 P1을 열린 채 둔다.

## 서명 형식과 단독 QA 검증기의 범위

서명 알고리즘은 `RSA-3072`·`SHA-256`·`RSASignaturePadding.Pkcs1` 한 가지다. 공개키는 `RSAParameters`의 정확 modulus/exponent 바이트로 가져오고 `RSA.Create()`, `ImportParameters(publicOnly)`, `VerifyHash(SHA256(payload), signature, HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1)`을 사용한다. 실제 서명 세션은 `SignHash`로 같은 해시·패딩을 쓴다. 이 선택은 `ImportSubjectPublicKeyInfo` 같은 런타임별 PEM API와 Unity 내부 API를 요구하지 않는다. 현 호스트는 PowerShell Core `7.6.5`와 `dotnet.exe`가 있으나 **키 생성·컴파일·Unity 실행은 이번 설계에서 하지 않았다**. 후속 구현 계약은 사용 .NET SDK/Unity `6000.6.0f1`의 정확 참조 조립과 메서드 서명을 정적 확인하고, 지원하지 않으면 다른 패딩/형식으로 암묵 전환하지 않고 중단해야 한다. 이번 단계는 새 `qa/tools/Test-Q0SignedPlanAuthority.ps1` 단독 검증기와 격리 합성 검수만 대상으로 하며 기존 Q0/엄격 감사/fixture 소스 네 파일의 구현 승인은 별개다.

서명 대상은 JSON 문자열 재직렬화가 아니라 다음 **정확 ASCII·LF·BOM 없음** 정규 바이트다. 각 SHA는 64개 대문자 16진수, nonce는 새로 만든 16바이트의 32개 대문자 16진수이고 다른 문자는 실패다.

```text
AGM-Q0-PLAN-V1
ContractSha256=<정확 승인 계약 SHA>
AuthoritySha256=<공개키와 검증 소스가 고정된 승인 기록 SHA>
PlanSha256=<원시 계획 파일 SHA>
Context=CurrentPublicationCleanClone
Nonce=<32자리 16진수>
```

마지막 줄에도 LF 한 개가 있다. 분리 승인 레코드는 `SchemaVersion`, 위 다섯 필드, `SignatureBase64`, `SignerRole=Astra`, 승인 시각, 정확 계획 경로만 허용한다. 중복/미지 키·비정규 Base64·RSA 길이 불일치·계획 경로 이탈·시간/문맥/nonce 누락은 거절한다. 기록 자체 SHA는 별도 수용 원장에 나중에 결속하고 자신 안에 넣지 않는다. nonce만으로 전역 일회성을 주장하지 않는다. 계획의 단일 실행 식별자·`CreateNew` 결과와 승인 기록의 일치 및 재사용 거절은 후속 실행 계약이 담당한다.

검증 순서는 외부 인증된 계약/승인 기록 SHA 확인 → **고정된 검증 소스 SHA·공개키 지문** 확인 → 레코드의 정확 스키마/중복 금지 → 계획 원시 바이트 SHA → 상기 정규 payload 재구성 → RSA 서명 확인 → 계획의 계약·권위 기록·문맥·실행 식별자·source/manifest 결속 확인이다. 어느 단계의 실패든 계획 본문을 Q0 권한으로 사용하거나 Unity/제품 입력을 읽기 전에 비정상 종료한다. 임의 caller가 서로 일치하는 계획·SHA를 가져오거나, 임의 다른 RSA 키/검증 소스로 새 레코드를 만들어도 외부 승인 기록·고정 소스와 불일치한다. 원래 역사 문맥 `HistoricalQ0Delta`로 서명된 기록, 지난 계획의 SHA/nonce를 새 현재 계획에 붙이는 시도, 계획·계약·기록·서명 한 바이트 변조도 거절한다.

격리 합성 시험은 서명 핵심 함수를 **입력 공개키가 명시된 내부 순수 함수**로 검증하되, 운영 진입점에는 공개키 교체 매개변수·`-SkipSignature`·시험용 우회가 없다. 정상 합성 키쌍/계획의 양성과 위 변조·다른 키·옛 문맥·누락/중복 필드·caller SHA 자체 일치만 있는 음성을 기록한다. 합성 개인키도 메모리 전용이며 출력하지 않는다. 실제 운영 진입점의 양성은 아스트라가 승인한 최종 키/레코드로만 검증한다. 합성 양성을 운영 승인으로 집계하지 않는다. 이번 후속 계약의 결과 플래그 `DependencyClosure`, `LunaReviewed`, `WholeAccepted`, `PublicationApproved`는 모두 거짓으로 남긴다.

## 서명 없는 대안의 한계와 인수 관문

서명 없이 최종 계획 SHA를 **이미 인증된 외부 Approved 문서**에 직접 고정하고 QA 검증기가 그 문서의 진정성과 SHA를 독립 확인할 수 있다면 기술적으로 같은 계획 승인 경계가 가능하다. 그러나 caller가 문서 경로와 SHA를 함께 주는 방식은 기존 P1 그대로이며, 검증 소스에 미래 계획 SHA를 하드코딩하면 계획이 검증 소스 SHA를 포함할 때 자기 지문 순환이 생긴다. 기존 저장소 안에 새 승인 파일을 쓰기만 하는 것도 인증 근거가 아니다. 실제 승인된 개정/서명된 외부 루트를 별도로 제공해야 하는데 지금 확인된 간단한 무서명 루트는 없으므로 **현 단계에서는 RSA 분리 레코드 후보를 권고**한다.

`REQ-PLAT-068` 후보의 `AC-PLAT-066`은 외부 승인 루트·고정 공개키/소스·정확 계획/계약/현재 문맥·서명 검증 및 임의 키/계획 거절, `REQ-PLAT-069`의 `AC-PLAT-067`은 소스→계획→서명→루나→수용의 비순환 동결과 단명 개인키 세션 실패 중단, `REQ-PLAT-070`의 `AC-PLAT-068`은 격리 합성 양성/음성·운영 우회 부재·게시 미수용 분리다. 원래 Q0 clean-clone Git 상태/188+377행·전체 9선택은 이 서명기만으로 충족되지 않는다. 그 검증은 이후 별도 Approved 구현 계약·실행·루나 독립 검수를 요구한다.
