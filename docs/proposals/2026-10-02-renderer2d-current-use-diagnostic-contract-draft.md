## 아스트라 승인 후보인 최소 실행 계약

1. **입력·도구 동결.** 이미 격리된 `output/u505-r1` 한 프로젝트에서만 새 Editor 진단 소스 `Assets/Editor/PublicationRendererCurrentUseProbe.cs`와 생성 `.meta`를 허용한다. 기존 `PublicationRendererGuidProbe.cs`·meta 및 v1/v2 출력은 보존한다. 제품 505 후보, 원본 534 경로/원문, 534 정규화 후보, 해당 실행본 안의 기존 505 파일, 위 다섯 프로젝트 자산/설정, `Packages/manifest.json`/`packages-lock.json`, URP/Core `package.json`·사용 소스의 SHA를 실행 전후 각각 기록한다. 새 진단 source SHA와 전체 바이트를 `artifacts/c4-renderer-current-use-probe-source-v1.cs.txt`에 먼저 보존하고 새 `.meta` GUID·SHA를 기록한다. 도구 source가 결과 JSON의 자기 SHA 또는 미래 루나 검수 SHA를 요구하지 않게 한다. 실행 전 실제 설치 패키지/API와 소스가 일치하지 않으면 컴파일·Unity 호출 전에 중단한다.
2. **현재 APV 여섯 자원.** Editor에서 `GraphicsSettings.currentRenderPipeline`, `GraphicsSettings.renderPipelineAsset`, `QualitySettings.renderPipeline` 및 로드된 전역 설정 자산의 실제 형식·경로·GUID/localFileID를 읽는다. `SerializedObject`의 실제 `ProbeVolumeDebugResources` 관리 참조 한 개를 엄격 식별하여 `probeVolumeDebugShader`, `probeVolumeFragmentationDebugShader`, `probeVolumeSamplingDebugShader`, `probeVolumeOffsetDebugShader`, `probeSamplingDebugMesh`, `numbersDisplayTex` 여섯 속성 각각의 존재·`ObjectReference` 형식·null/실제 객체 형식·경로·GUID/localFileID를 기록한다. 여섯 현재 GUID가 각 대응 설치 Core `.meta`와 정확히 연결되는지도 검증한다. 중복/부재/타입 불일치는 실패 또는 미관측으로 남긴다. 내부 `ProbeVolumeDebugResources`를 직접 형식 참조하거나 `TryCreateDebugRenderData`를 인위 호출하지 않는다. 이 관측은 **자원 공급 가능성**만 증명한다. APV 디버그 실제 소비를 주장하려면 조건부 분기 활성화와 그 호출의 별도 실제 관찰이 필요하며, 이번 범위에서는 달성하지 못하면 미관측이다.
3. **Renderer2D의 실제 선택.** 현재 유효 파이프라인이 `UniversalRenderPipelineAsset`의 정확 `UniversalRP.asset`이고 `rendererDataList`의 기본 0번이 같은 `Renderer2D.asset` 객체임을 public 조회·`AssetDatabase.TryGetGUIDAndLocalFileIdentifier`로 확인한다. 제한 진단 카메라의 실제 `UniversalAdditionalCameraData.scriptableRenderer`가 `Renderer2D`이고, 다른 renderer fallback 경고가 없으며 렌더 시작·종료 콜백이 그 카메라에 발생해야 한다. 단순 YAML의 0번 또는 로드 객체 존재만으로 선택 성공을 기록하지 않는다. `UniversalRenderPipelineAsset.rendererDataList`와 `UniversalAdditionalCameraData.scriptableRenderer`는 설치 URP 소스의 공개 속성이지만 getter가 렌더러를 지연 생성할 수 있으므로 읽는 시점과 렌더 전후를 분리 기록한다.
4. **실제 조명 렌더와 falloff.** 진단 실행본에서만 저장하지 않는 임시 카메라·작은 `RenderTexture`·Sprite/`Light2D`를 한정 생성하고 `try/finally`에서 해제한다. 조명 batch를 사용하도록 실제 2D 조명/정렬 레이어를 구성한다. 그래픽 장치가 있는 Windows Editor 표면에서만 `RenderPipeline.SupportsRenderRequest`를 확인한 뒤 `RenderPipeline.SubmitRenderRequest(camera, new UniversalRenderPipeline.SingleCameraRequest { destination = rt })`의 공개 API를 한 번 호출한다. 설치 Unity `UnityEngine.CoreModule.xml` 48309–48314·48366행과 URP `UniversalRenderPipeline.cs` 675–681·692–710·2880–2890행이 이 요청 형식의 정적 근거다. `-nographics`에서 렌더를 시도하거나 제거된 `Camera.Render` 경로로 우회하지 않는다. 콜백의 실제 카메라·렌더 완료, 출력 픽셀/읽기 성공, `Shader.GetGlobalTexture("_FalloffLookup")` 또는 해당 렌더 구간의 정확 전역 결속 관측, 생성된 비null 텍스처와 렌더 오류0을 함께 요구한다. 내부 `Light2DLookupTexture.GetFallOffLookupTexture_Rendergraph`를 직접 호출해 생성 사실을 제조하지 않는다. 전역 텍스처를 실제 시점에 관찰할 수 없다면 정적 호출 연결과 렌더 성공만 기록하고 **실제 falloff 소비는 미관측**으로 남긴다.
5. **지원 표면과 판정.** 위 렌더 관측은 현 격리 프로젝트·Unity `6000.6.0f1`·Windows Editor·URP/Core 설치 버전·한정 2D 조명 장면에만 적용한다. Unity는 새 Approved 계약 후 한 번만 `-batchmode -quit -projectPath output/u505-r1 -executeMethod PublicationRendererCurrentUseProbe.Run`으로 호출하되 그래픽 장치가 필요하므로 `-nographics`를 사용하지 않는다. 진단 소스의 정적 API/조립 확인과 컴파일 실패·그래픽 장치 부재·render request 비지원·콜백/전역 텍스처 미관측은 결과에 그대로 남기고 재시도·다른 API 패치·자산 수정은 별도 승인 없이는 하지 않는다. 콘솔/로그에서 컴파일, missing shader/texture/mesh, render graph, 2D light, 파이프라인 fallback의 실제 오류를 분류하고 원래 licensing/shutdown 잡음과 분리한다. 렌더 오류0도 모든 장면/플랫폼 무영향이나 역사 GUID7 해석 성공을 뜻하지 않는다.
