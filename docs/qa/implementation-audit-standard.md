## 1. 필수 분류와 세부 항목

### 아트

- 인물 원화: 도언·세령·주요 인물별 채택 디자인, 초상·표정·대화용 이미지.
- 적·보스 원화: 일반 적 유형과 CH1~CH8 보스별 디자인. 진보스는 별도 행.
- 캐릭터 스프라이트: 인물별 좌우 방향과 대기·이동·점프·대시·벽차기·공격·피격·사망 등 해당 승인 동작.
- 적·보스 스프라이트 및 동작: 유형별 패턴·피격·사망·단계 변화.
- 의상·외형: 의상별 미리보기·게임 내 동작 패키지. 원화 수용과 사용 가능한 외형 패키지를 구분한다.
- 배경·타일·지형·사물: 챕터별, 마을·상점별. 원본 확보와 프로젝트용 파생본을 구분한다.
- 화면 이미지·아이콘·글꼴·효과: 메인화면, 설정, 체력·조준·상호작용 표시, 공격·전이 효과.
- 컷신·영상: 장면별 실제 채택·재생 준비 범위. 단순 시안 영상과 게임 내 연출을 구분한다.

### 소스 구현

- 공통 조작: 이동·점프·대시·벽차기·입력·조준·카메라.
- 전투: 기본 공격·공격 동작 판정·피해·피격·사망·적 행동·보스 패턴·단계별 처리.
- 스킬: 무게 전이·회수, 압착 판결, 공동 기준면 및 후속 승인 스킬별 개별 행.
- 원정: 방 조립·시드·방 이동·위험·보상·실패·복귀·재출정.
- CH1~CH8: 챕터별 진행 제어·전투 사건 연결·선택·장면 사건·성공/실패/완료 처리. 해당 챕터의 전용 구현을 세부로 펼친다.
- 서사·관계: 대화·선택·유대·약속·분기·엔딩·재시도별 범위.
- 저장·시작: 저장·로드·복구·새 게임·이어가기·입력 재지정.
- 화면 기능: 메인 메뉴·설정 적용·일시정지·안내·종료.
- 마을·상점·옷장: 마을 상호작용·상점 거래/해금·의상 미리보기/착용/저장. 승인되지 않은 제품 기능은 승인 상태를 표시하고 구현하지 않는다.

### 유니티 모델·장면 구성

- 캐릭터: 인물별 프리팹·충돌·렌더러·애니메이션·입력/상태 연결.
- 일반 적·보스: 유형별 실제 화면 표시·판정·행동·전투 연결.
- 메인화면: 시작 장면·메뉴·초기 포커스·새 게임·이어가기의 실제 목적지 연결.
- 설정: 화면·음량·입력 화면과 실제 적용·저장·복원.
- CH1~CH8 내부: 지형·방·배치·입출구·위험·보상·보스·연출·장면 전환을 각각 구분.
- 마을·거점: 인물 배치·대화·출정·실패 복귀·지속 변화.
- 상점·옷장: 화면·객체·상호작용·실제 기능 연결.
- 전투 표시: 체력·조준·공격/피격/스킬 효과·입력 안내.
- 선택·컷신·엔딩: 실제 장면·재생·입력 잠금·완료 및 다음 상태 연결.
- 빌드·시범 플레이: 활성 시작 장면 목록·현재 소스 빌드·성공/실패/재시도·실제 완주 증거.

음원·음향과 검증·게시·개발 도구는 보조 표로 보고한다. 도구 통과율, 시험 수, 문서 수, 서명·게시 성공을 아트·소스 게임 기능·유니티 장면의 퍼센트로 더하지 않는다. 음향의 게임 내 연결은 해당 장면 항목의 근거로 참조할 수 있다.

## 2. 퍼센트 산정

### 고정 목표 목록

최초 감사에서 데모와 본편을 별도로 나누어 대상 ID, 산출물/행동 단위, 목표 수량, 완료 조건, 집계 여부와 가중치를 기록한다. 대상은 캐논·승인 명세·현재 승인 계약에서 도출한다. 본편 검토 중 내용은 계획임을 표시한다. 파일 수·원화 장수·시험 수를 게임 전체 분모로 쓰지 않는다.

하나의 항목이 여러 단위라면 단위를 먼저 나눈다. 예: 세령 대기 좌우 프레임, 보스별 패턴, 챕터별 진행 연결. 개별 단위가 아래 네 단계를 어디까지 연속 충족했는지 근거로 0/25/50/75/100점을 부여한다. 부분 만족은 단위를 분해해 계산하고, 감으로 63% 등의 수치를 만들지 않는다.

| 점수 | 아트 단위 | 소스 단위 | 유니티 단위 |
|---|---|---|---|
| 0% | 대상 제작물 없음 | 해당 동작의 구현 없음 | 대상 객체/화면/장면 없음 |
| 25% | 식별 가능한 시안 제작 | 실제 부분 동작 코드 구현 | 실제 객체/프리팹/화면/장면 구성 |
| 50% | 해당 원화/원본 디자인 채택, 필요한 구성 제작 | 정의한 단위의 정상 동작과 필수 오류 경계 코드 구현 | 해당 단위의 필수 참조·소스·자산 연결 완료 |
| 75% | 단위의 프레임/방향/규격/권리/파생본 준비와 제작자 검사 완료 | 해당 정확 소스의 의미 있는 집중 실행 검사 통과 | 실제 실행에서 표시·동작·전환을 관측하고 집중 검사 통과 |
| 100% | 해당 단위의 독립 시각·기술 검수 및 수용 완료 | 해당 단위의 AC 독립 검증 및 아스트라 수용 완료 | 해당 단위의 실제 장면/필요 빌드 독립 검수 및 수용 완료 |

단위에 불필요한 조건을 억지로 추가하지 않는다. 원화는 원화의 채택·검수까지가 목표이며, 스프라이트·유니티 연결은 별도 단위다. 순수 코어 코드의 100%는 그 코어의 정확 계약 수용을 뜻하고 챕터·장면의 완성을 뜻하지 않는다. 기획 문서만 작성된 소스 단위는 0%이며, 원화 시안 25%와 구분한다. 미검증 존재를 미구현으로 오인하지 않고 점수 단계와 검증 상태를 함께 표시한다.

- 항목 구현도 = 각 목표 단위의 점수 × 사전에 고정한 가중치의 가중평균. 동일 성격 단위는 기본 동일 가중치. 소수 첫째 자리까지 표시한다.
- 분류 구현도 = 해당 분류의 집계용 최하위 항목의 가중평균. 요약 행과 참조 행은 다시 더하지 않는다.
- 전체 구현도 = 완전한 대상 목록과 범위별 가중치가 고정된 경우에만 아트·소스·유니티의 가중평균을 계산한다. 초기 보고 지표의 기본 분류 가중치는 각각 1/3이며, 노동시간/제작비 비율이라는 뜻이 아니다. 아스트라가 다른 가중치를 채택하면 이유와 개정을 기록한다.
- 분모·제작량이 미정이면 퍼센트는 `산정 불가`로 표시하고 이유·현재 확인 수량을 쓴다. 조사하지 않은 항목을 0%로 처리하거나 알려진 항목만으로 전체를 100%까지 정규화하지 않는다. 필요한 경우 고정된 일부 범위의 퍼센트만 명시하고 전체는 산정 불가로 남긴다.
- 범위 밖은 `해당 없음`, 포함하되 승인 전이면 `승인 전`을 별도 표시한다. 승인 전이라는 이유로 본편 목표에서 숨기지 않는다.
- 공유 소스·공유 자산은 원래 소유 항목에만 집계한다. 챕터별 표에는 공통 기능을 참조하고 챕터 전용 구현/연결을 평가해 중복 계상을 피한다.
- 검수 기준 변경·자료 훼손 등으로 점수가 내려가면 하락을 숨기지 않고 이유를 쓴다. 과거 수용과 현재 바이트의 증거 적용 여부도 구별한다.

이 퍼센트는 목표 단위의 제작·구현 성숙도 지표다. 소비한 시간, 앞으로 필요한 시간, 플레이 분량, 기능의 재미, 출시 준비도를 직접 나타내지 않는다. 기존 대화의 10~15%, 40% 같은 근거 없는 추정치를 최초 비교 기준으로 재사용하지 않는다.

## 3. 보고 서식과 비교

### 필수 첫 표 — 1챕터와 전체8챕터

2026-10-08 사용자 지시에 따라 첫 요약 표에 `분류 | 1챕터 기준 | 전체8챕터 기준 | 산정 단위·근거`를 항상 병기한다. 공통 기능47행 등의 일부 평균을 이 두 범위의 완성도로 대신하지 않는다. 상세 제작량 전체가 미정인 상태에서 유한 비교가 필요하면 [대상 목록 개정2](../verification/implementation-audits/inventory-v2.md)의 **챕터 전달 패키지 성숙도**를 사용하고 지표 이름을 생략하지 않는다. 이는8챕터×아트/전용소스통합/유니티통합의24개 전달 묶음에 동일 가중치를 부여한 단계 지표이며, 파일·노동시간·전체 세부 산출물의 완료율이 아니다.

첫 표와 같은 위치에 실제 완주 수(1챕터0/1 또는1/1, 전체0~8/8), 최신 사용자용 빌드, 세부 제작량 기준 전체 완료율의 산정 가능 여부를 표시한다. 공통 기반·메뉴/설정·저장·옷장/상점 등 챕터 밖 범위는 별도 표에 남기고 챕터별로 복제 합산하지 않는다. 챕터8의 조건부 진보스·엔딩은8장 패키지에 포함하며 삭제하지 않는다. 기존 세부 항목·목표·REQ/AC는 유지한다. 새로운 분모의 점수를 과거47행 수치와 직접 비교하거나 제품 구현 진척으로 표시하지 않는다.

[고정 서식](./implementation-audit-template.md)을 사용한다. 모든 필수 항목을 남기고 해당 없음·산정 불가도 이유와 함께 표시한다.

- 감사 날짜/관측 시각, 데모/본편 범위, 서식·대상 목록 개정, 비교 대상 보고서, 코드·장면·빌드 기준을 명시한다.
- 분류 요약과 상세 표 모두 `이전 % | 현재 % | 증감(%p) | 근거 | 남은 작업`을 포함한다.
- 상세 표에 고정 ID·대상 단위/분모·점수 구성·승인/구현/실행/독립수용 상태·REQ/AC를 기록한다.
- 첫 보고는 이전과 증감을 `최초 기준`으로 표시한다. 가짜 증가량을 만들지 않는다.
- 이후 같은 범위·분모·가중치로 현재−이전을 계산한다. 예: 25%→50%는 +25%p다.
- 목표 추가·제외·가중치 변경은 `범위 변경` 표로 분리하고 기존 범위의 진척과 개정 후 수치를 함께 제공한다. 기준 변경으로 생긴 증가를 구현 진척으로 표시하지 않는다.
- 현재 작업은 산출물 이름, 게임 기능/아트/유니티/도구 중 분류, 성공 조건, 최근 결과, 다음 작업을 써서 사용자가 무엇을 구현하는지 알 수 있게 한다.
- 반복 원장은 실제 실패 원인·제품 변경 여부·새 증거·재실행 근거·다음 중단/종료 조건을 짧게 쓴다. 반복 횟수나 대기 시간은 기록이 있는 범위만 보고한다.
- 사용자 요약에는 분류별 수치, 이전 대비 변한 항목, 변하지 않은 플레이 범위, 현재 작업과 다음 전달물을 포함한다.

## 4. 일일 감사와 별도 요청

사용자가 구현 상태/진척 감사를 요청하면 이 서식을 항상 사용한다. 감사가 특정 범위면 상세는 그 범위로 제한하되 전반 요약과 적용 범위를 명시한다.

현재와 향후 구현 세션의 정기 진척 감사는 매일 한국시간(Asia/Seoul) 오전 8시 하루 한 번이다. 구현부·완료·독립 수용·빌드/플레이·범위 변경·실패 경로 변경·인계마다 진척 감사를 추가하지 않는다. 해당 과정의 통상 작업 기록과 필수 검사는 유지하고 다음 일일 보고에 모은다. 감사 대화에서 일일 보고를 작성하며 구현 세션은 같은 날짜의 보고를 중복 작성하지 않는다. 변화 없는 날도 변화 없음과 현재 작업을 보고한다.

예정 시각과 실제 관측 시각, 전일 오전 8시 보고의 날짜·링크를 명시하고 같은 분모로 비교한다. 첫 예약 감사는 `2026-10-03-02.md`와 `inventory-v1.md`를 기준으로 삼고 실제 관측 간격이 24시간과 다름을 표시한다. 전일 보고가 없으면 직전 실제 보고의 날짜·간격을 밝히며 전일 수치를 추정하지 않는다. 동일 한국 날짜의 일일 감사가 이미 있으면 중복 실행·작성하지 않는다. 별도 사용자 요청에 따른 수동 감사는 계기를 명시한다.

변경 항목만 새 증거를 대조하고 미변경 항목은 이전 증거를 참조한다. 감사 때문에 전체 Unity 회귀·새 빌드·검증 도구 개발·키/서명·원격 게시·별도 장기 작업을 실행하지 않는다. 구현 작업을 잠그거나 중단하지 않으며, 관측 중 변경되어 증거가 혼재하면 관측 시각과 미검증을 명시한다. 최초 전수 목록과 이후 증분 보고를 구분한다.

감사 보고는 기존 승인·독립 수용을 대신하지 않는다. 구현자가 자기 결과를 독립 검증했다고 표시하지 않는다. 감사에 실제 새 독립 에이전트가 필요할 때 ADR-0037의 허용 모델을 따른다. 보고마다 독립 에이전트를 반드시 새로 만들 필요는 없고, 기존 독립 증거의 적용 상태를 정확히 표시하면 된다.

## 5. 추적과 제출

- `REQ-AUD-001`: 아트·소스·유니티 및 필수 세부 항목을 분리한다. `AC-AUD-001`: 제출 표에 필수 분류와 챕터 CH1~CH8 행이 있고 누락은 이유가 명시된다.
- `REQ-AUD-002`: 근거·분모·고정 단계로 퍼센트를 산정한다. `AC-AUD-002`: 수치마다 단위/점수/근거가 있어 재계산 가능하고 불명 항목은 임의 수치가 아니다.
- `REQ-AUD-003`: 이전 대비 변화와 범위 변경을 분리한다. `AC-AUD-003`: 비교 보고/개정이 명시되고 증감이 재계산되며 최초 기준/범위 변경을 구별한다.
- `REQ-AUD-004`: 매일 한국시간 오전 8시 하루 한 번 전일 대비로 보고하며 별도 사용자 감사 요청은 예외다. `AC-AUD-004`: 일일 보고에 예정/실제 시각·비교 날짜/간격·현재 작업·제품/도구 구분·다음 작업이 있고 구현부별 중복 진척 감사를 하지 않는다.
- `REQ-AUD-005`: 가벼운 증분 감사와 독립 수용 원칙을 유지한다. `AC-AUD-005`: 실제 실행 여부·재사용 증거·미검증·담당을 명시하고 불필요한 전체 재실행을 하지 않는다.

보고서는 `docs/verification/implementation-audits/`에 `YYYY-MM-DD-NN.md`로 보존한다. 목표 목록은 첫 기준 보고서 또는 같은 디렉터리의 `inventory-vN.md`에 둔다. 새 보고를 쓸 때 이전 파일을 덮어쓰지 않는다. 최신 보고 링크는 `docs/verification/implementation-audits/README.md`에서 관리한다. 현재 규칙 추가는 보고 절차 승인이지 게임 코드 최초 게시나 게임 요구사항 변경 승인이 아니다.
