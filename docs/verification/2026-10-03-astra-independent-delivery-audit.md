# 2026-10-03 아스트라 독립 구현·전달 감사

이 감사는 사용자가 요청한 별도 아스트라(`gpt-6-astra`)의 읽기 전용 조사다. 기존 구현·승인·검증 담당자의 결과를 그대로 반복하지 않고 현재 코드·장면·빌드 설정, 과거 실행 자료의 원문과 지문을 대조했다. 이 파일 외에는 변경하지 않았다. 새 Unity 실행, 빌드, 수동 플레이, 프로세스 종료, 원격 조회·게시, 키 생성·서명, 기존 승인 변경은 수행하지 않았다. 추가 작업자는 호출하지 않았다.

관측 기준은 2026-10-03의 로컬 작업 공간이다. 다른 작업의 진행 중 변경 가능성이 있으며, 이 문서는 전체 작업 공간을 잠근 원자적 시점 기록이 아니다. 완료율·총 투입 시간·납기는 산정하지 않았다. 과거의 근거 부족한 비율·기간 추정은 재사용하지 않는다.

## 판정

**게임 기능 구현은 실제로 존재한다. 그러나 검증된 여러 부품을 사용자가 시작부터 성공·실패·재시도까지 플레이하는 게임으로 통합한 상태는 확인되지 않는다.** 최근 진척은 새 게임 초기화의 안전한 실행 연결과 최초 코드 게시를 위한 출처·복제·검증 도구에 집중되어 있다. 이를 새 방·전투 콘텐츠·사용자용 게임 빌드의 증가와 같은 진척으로 보고하면 실제 상태를 오해하게 된다.

반복은 모두 헛수고가 아니다. 저장 손상 방지, 취소·재실행 권한 폐쇄, 실제 결과 출처 확인은 의미 있는 기능 품질 진척이다. 동시에 잘못된 시험 중단 판단, 정상 입력을 거절하는 검증 도구, 늦게 발견한 실행 환경 전제 때문에 **게임 기능을 추가하지 않고 도구를 다시 고치는 반복도 실제로 있었다.** 이 반복과 과도하게 잘게 나뉜 승인 경계가 사용자 체감 진척을 가리고 있다.

## 최근 실제로 구현하는 대상

2026-09-28~10-01은 새 게임 확인·취소·재무장, 디스크 초기화와 메모리 교체를 잇는 C3/C4 및 그 시험·증거 도구가 중심이다. [ADR-0036](../adr/0036-staged-confirmation-and-execution-acceptance.md)은 C3가 C4 실제 결과를 요구하면서 C4가 C3 독립 수용을 선행 요구하는 순환을 인정하고 단계적 수용으로 해소했다. 이 작업은 기능 안전성에 기여했지만, 계약 경계가 실행 순서를 막은 실제 사례이기도 하다.

2026-10-01~03은 [ADR-0038](../adr/0038-forward-provenance-for-initial-code-publication.md)에 따라 최초 코드 게시 후보의 현재 바이트 출처, 줄바꿈 정규화, 필수 의존 입력, 렌더러 참조 진단, 깨끗한 복제와 Q0 서명 실행 도구로 이동했다. 과거 428개 출처 공백과 14개 미입증 전이를 최신 실행 통과로 소급하지 않기로 한 판단은 타당하다. 다만 현재 바이트의 검증 경로 자체가 상당한 개발 대상으로 커졌다.

Q0의 최신 상태를 r1 하나로 설명하면 부정확하다.

- [10-03 r1 실패 기록](2026-10-03-q0-r1-operational-pre-sign-failure.md): 실제 53필드 계획 생성 중 빈 배열이 null로 바뀌어 `$prefix.Count`에서 실패했다. 이 세대는 서명 요청 0·실행 승인 0·아홉 실행 0이다.
- [R4 복구 계약의 R3 역사](../specs/work-contracts/2026-10-03-q0-r4-capture-boundary-recovery.md): R3는 새 키 1·서명 1·승인 1·소비 1까지 진행했으나 첫 입력 캡처가 정상 기대행 파일의 접미사를 산출물로 오인하여 거절했다. Unity 운영 실행과 아홉 출력은 0으로 기록돼 있다. 이번 감사는 R3의 `execution-plan.approval.json` 및 `execution-consumed.json` 존재와 소비 원문을 직접 확인했다. 원격 병합은 조회하지 않았으므로 해당 부분은 로컬 기록의 보고 내용이다.
- R4 관측: `output/q0-trusted-child-evidence-r4/`의 준비·채널·스키마 회귀·Unity 지원 자료가 존재한다. 채널·스키마·Unity 지원 JSON은 `Result=PASS`, `WholeAccepted=false`다. 준비·채널·스키마 자료의 운영키 생성 값은 거짓이다. 관측 당시 그 디렉터리에 실행 계획·서명·소비·큐 최종 결과는 없었고, R4 루나 디렉터리 직속 결과 파일도 없었다. 준비 지원 통과를 운영 아홉 실행 통과로 확대하지 않는다. 후속 작업이 계속될 수 있으므로 현재 진행 담당자는 이 관측 이후 결과를 별도로 갱신해야 한다.

관련 추적은 `REQ-PLAT-061/062/068/069/070`, `AC-PLAT-059/060/066/067/068`이다. 이 작업의 성공은 재현 가능한 코드 검증·게시 준비를 개선한다. 방·적·선택 콘텐츠를 늘리는 작업은 아니다.

## 과정의 구조적 문제와 책임

독립 검수는 실제 결함을 잡았고, 범위를 넘는 수용을 방지했다. 이 원칙을 없애는 것이 해결책은 아니다. 문제는 **게임 전달 목표를 소유하는 수준의 우선순위와 통합 계획이, 아주 작은 검증 경계를 승인하는 작업에 밀린 점**이다.

아스트라는 계약·배분·최종 통합의 소유자이므로 이 우선순위 문제를 개별 구현자나 검수자 탓으로 돌릴 수 없다. 테라가 승인 범위에 없는 게임 진입을 임의로 만들 수 없고, 루나가 명시된 기준을 임의로 생략할 수도 없다. C4의 의도적인 비게임플레이 범위를 완료한 뒤 다음 제품 연결 계약을 잡는 책임은 총괄에 있다.

문서의 최신 상태도 분산돼 있다. 예를 들어 원본 C4는 검토 상태를 보존하고, 별도 r4 계약이 구현 권한을 소유하며, 10-01 수용문이 최종 수용을 기록한다. 문서 지도에는 과거 진행·차단 상태가 길게 누적된다. 이는 역사를 보존하지만 다음 작업자가 현재 상태를 잘못 읽기 쉽다. 이번 감사에서도 r1만 읽으면 서명 0으로 오인할 수 있었고, R3 소비와 R4 준비까지 추적해야 현재 범위가 드러났다.

계약·검증 문서 수와 버전 수는 실제 노동 시간이나 생산성 지표가 아니다. 다만 여러 작은 경계가 별도 승인·지문·고정 세대·실행 복제본을 요구하는 구조는 변경의 종속 비용을 키운다. 이 복잡도가 현재 위험과 사용자 전달 목표에 비례하는지 아스트라가 재평가할 필요가 있다. 본 감사는 암호화 승인 체계나 기존 계약을 폐기하도록 승인하지 않는다.

## 개선 순서

1. **최신 상태를 한 표로 유지한다.** 기능별 사용자 동작, 현재 승인 계약, 구현 지문, 독립 검수, 통합/빌드 상태, 다음 한 작업, 담당자를 연결한다. 과거 기록은 보존하되 현재 표에서 최신 수용문과 현재 실패 세대를 바로 찾게 한다. 완료 보고에서 기능 구현·통합 플레이·검증 도구·게시 준비를 구분한다.
2. **운영 실행 전 입력 준비를 실제 함수로 확인한다.** 정상 전체 계획, 빈 배열·경계 정수·문자 인코딩·경로·정상 기대행 파일을 키 없는 생산 경로로 검사한다. 모의 경계는 명시하고 마지막 정상 입력이 실제 첫 캡처를 통과했는지를 독립 검수한다. 기존 계약에 없는 변경은 아스트라가 일관된 보정 계약으로 승인한다.
3. **시험의 진행 여부를 로그 침묵으로만 판단하지 않는다.** 실행기 완료 콜백·시험 시작/종료·실제 프로세스 종료를 관측하고, 이미 확인된 시험 시간과 전체 상한을 사용한다. 환경 실패·검사 도구 오류·게임 실패를 분리 기록한다. 새 증거가 생긴 경우에만 재실행한다.
4. **제품 통합 작업을 명시적으로 배정한다.** 출처·게시 검증이 진행되는 동안 충돌 없는 별도 승인 범위에서 허브 진입→한 전투 구간→결과→재시도의 연결 설계를 진행한다. 구현은 테라, 독립 검수는 루나, 통합 수용은 아스트라가 유지한다. 게시 준비의 통과를 제품 진입의 자동 선행조건으로 묶어 두지 말고 실제 의존성을 근거로 구분한다.
5. **도구 반복의 중단 기준을 둔다.** 같은 입력·환경 문제로 반복 실패하면 전체 회귀를 더 돌리기 전에 최소 재현과 원인 판별을 완료한다. 매번 별도 초미세 계약을 추가하기보다 같은 위험·같은 소유자의 일관된 보정 범위를 묶어 승인한다. 회귀 재사용은 명시적 영향 분석과 독립 수용을 거치고, 필요한 시험을 임의로 생략하지 않는다.
6. **다음 전달물을 실행 파일과 실제 플레이 증거로 정의한다.** 기능 개수·시험 합계보다 시작 방법, 조작 가능한 대상, 성공·실패 결과, 재시도와 현재 바이트의 빌드를 완료 조건에 둔다. 짧은 체험을 먼저 만들 경우 기존 데모 전체 수용 기준을 줄이지 않고 별도 한정 계약으로 관리한다.

## 첫 실제 플레이를 위해 필요한 범위

가장 작은 조작 가능한 전달물에는 시작 장면과 게임 진입 연결, 플레이어·적·지형의 식별 가능한 표현, 입력 안내와 체력/피격/상호작용 피드백, 한 이동·전투 구간, 성공 또는 실패 뒤 재시도, 해당 장면을 포함한 현재 바이트 빌드, 독립 실행·플레이 검수가 필요하다. 기존 부품을 연결하고 부족한 표시·목적지를 구현하는 범위이며, 이를 완료했다고 승인된 전체 데모가 완성되는 것은 아니다.

[전체 데모 계약](../specs/vertical-demo/00-spec-index.md)의 `REQ-SCOPE-001..004`, `AC-SCOPE-001..004`를 충족하려면 추가로 다음을 완주해야 한다.

- 거점 1개와 수작업 방 풀 6개·원정당 4개 방의 실제 저작·도달성·전환: `REQ-ROOM-001..007`, `AC-ROOM-001..006`.
- 일반 적 두 유형과 보스의 실제 원정 배치, 방 진행 및 보스 이후 흐름.
- 인간성 선택과 선택별 두 기술, 봉쇄선 통과, 완료 확정과 세령의 첫 등장: `REQ-CHOICE-001..007`, `AC-CHOICE-001..004` 및 `AC-SCOPE-001`.
- 실패 시 원정 자산 초기화·보존 상태 유지·거점 복귀·재출정: `AC-SCOPE-002`.
- 현재 빌드의 콘텐츠 수량 대조와 독립 실제 완주: `AC-SCOPE-003/004`, `AC-PLAT-002/005`의 해당 범위. 명세의 12~18분은 완성 후 플레이 시간 수용 기준이며 개발 소요기간 예측이 아니다.

현재 증거로 말할 수 있는 결론은 부품 구현의 실재, C3/C4의 제한 수용, 초기 환경 빌드의 잔존, 통합 플레이 수용의 공백이다. 정확한 총 개발량·실작업 시간·남은 제작량이 산정되지 않았으므로 완료율이나 완료 날짜를 제시할 근거는 없다.
