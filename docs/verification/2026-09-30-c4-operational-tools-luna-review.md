# C4 운영 도구 독립 정적 검토

검토 범위는 2026-09-30 현재의 운영 스크립트 다섯 개와 Approved QA r2, 선행 선택 형식, 기존 377행 비교의 제한 분기다. Unity, 컴파일, 실제 QA/큐, Git, 네트워크는 실행하지 않았다. PowerShell 구문 분석은 다섯 파일 모두 오류 0이었다. 이는 실제 실행 검증이 아니다.

P1 — 신규 C4 행 비교와 실제 XML의 연결이 검증기에서 닫히지 않는다. `c4-verify-run.ps1` 20행은 `row.XmlBinding`의 자체 파일·SHA를 검사하고 `EvidenceMatched`, stem, 예상 원장만 확인한다. 그 binding이 실행 계획의 실제 `$out.Xml`과 같은 경로·SHA인지, 또는 검증 결과의 `XmlBinding`과 같은지 비교하지 않는다. 행 비교 파일이 다른 유효 XML을 가리키도록 바뀌어도 이 분기 자체는 거절을 보장하지 않는다. QA r2의 행 비교 결과와 실행 XML의 정확 결속 요건을 충족했다고 볼 수 없다. 검증기에서 세 결속의 경로와 SHA를 정확 비교해야 한다. 기존 Matrix91 전용 `C4-LegacyRows` 경로는 실제 `$out.Xml`을 직접 받아 대조하므로 이 지적과 별개다.

P1 후보 — 선택 파서의 추가 직접 입력이 입력 포착 목록에 포함되는지 강제하지 않는다. 보정된 선택 생성기는 `EnumSourcePaths` 파일들을 읽고 그 경로와 SHA를 선택의 `ParserEvidence.EnumSources`에 기록한다. 실행 사전 검사는 계획의 선택·원장·도구 등을 입력 목록과 대조하지만, 중첩된 `EnumSources`의 각 경로가 `InputPathList.Paths`에 있는지는 확인하지 않는다. 현재 열거 대상이 모두 포착 범위인 `Assets` 아래로 제한된다는 검사는 이 다섯 도구에서 찾지 못했다. 따라서 외부 직접 입력이 허용될 수 있다면 그 파일의 전후 고정·동결 검증이 빠진다. 입력 목록 포함을 강제하거나 열거 경로를 포착된 범위로 제한해야 한다. 실제 최종 `EnumSourcePaths` 목록이 전부 입력 목록에 포함된다는 별도 동결 증거가 있으면 이 후보는 그 범위에서 닫을 수 있다.

이전 selection-parser P1은 현재 바이트에서 정적으로 닫힌 것으로 판단한다. 이전 구현은 모든 열거 소스의 모든 enum을 명시 정수로 파싱해 실제 Bridge의 무관한 암시형 private enum에 걸릴 수 있었다. 현재 구현은 `[TestCase]` 인자에서 참조된 enum만 파싱하며, 참조 enum의 명시 정수값·이름 및 값의 유일성, 별칭·중복·미지원 문법 거절은 유지한다. 실제 브리지의 무관한 enum은 참조되지 않으면 이 제한 파서의 실패 원인이 되지 않는다. 구현자 측 제한 점검은 10/10이라고 보고됐지만 독립 재실행이 아니며, 최종 선택 출력과 Unity 실행도 확인하지 않았다.

나머지 운영 경계는 정적 검토에서 규약에 부합했다. 큐는 프로젝트별 배타 잠금을 잡고 단일 실행을 순서대로 처리하며, 선택 실행의 실제 종료·행 검증을 확인하기 전 다음 실행을 시작하지 않는다. runner는 큐의 자식 실행만 허용하고, 실제 편집기 후보를 완전한 프로세스 목록에서 경로·실행 인자·생성 시각으로 연결하며, 편집기 종료값과 QA 도구 및 runner 종료값을 별도 기록한다. 관찰 만료 시 프로세스를 종료시키지 않고 실패로 멈춘다. 최종 증거는 기존 파일을 덮지 않는 생성 방식이다.

입력 포착기는 입력 경로 목록의 정렬·중복 및 직접 열거된 범위의 파일 집합을 확인하고, 자기 자신과 실행 산출물을 재귀 포착하지 않는다. 선행 원본 선택 여섯 개는 경로·SHA·키 형식·이름 배열에 고정 결속되며, 91/149 부분 실행은 기존 240 전체에 대해 서로소 집합과 원래 부분 순서를 확인한다. Matrix91에서는 고정된 기존 377행 검사기와 원래 결과 스키마를 사용하고, 새 C4 행 스키마로 변환하지 않는다. 선택 생성기의 수정은 이전 테스트 선택을 대체하지 않으며 로컬 점검 보고는 생성기 동작의 보조 근거일 뿐 실제 NUnit 결과가 아니다.

`barrier.ordinaryWriterBlocked=No`는 reset barrier가 실제 ordinary writer를 막지 않았다는 의미로만 해석해야 한다. marker 또는 lease가 없다는 사실만으로는 다른 저장 실패 원인을 배제하지 못하므로 이 값의 근거가 되지 않는다. 요구된 실제 writer 검사가 있는 행에서 안전한 임시 루트에 대한 실제 Save 관측이 없다면 `Unknown`이어야 한다. 반대로 `No`를 전체 프로필 저장 성공의 주장으로 넓혀서도 안 된다.

현재 정적 판정은 P0 0건, 확정 P1 1건, 조건부 P1 후보 1건이다. Unity·컴파일·큐·실제 선택 생성은 검증하지 않았으며 이 기록은 도구 실행 또는 C4 수용이 아니다.
