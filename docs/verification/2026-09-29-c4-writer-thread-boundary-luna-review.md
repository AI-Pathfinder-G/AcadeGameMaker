# C4 writer·thread containment 경계 독립 검토

검토 대상 `docs/proposals/2026-09-29-c4-writer-and-thread-containment-boundary.md` 확인 SHA-256은 `6E906DCC74DBE298D258EE279830B56CBFD00D2B2E7263D862F75CA8702C4691`이다. R2 초안 `A549466BBC08B69DFE576AFB391CAAA1473355982771E9C0613BBE940A83EA7A`, C4 Review 계약 `3F29B8BC7D3F0172717C0FC94101BF4086FEE1FE475B65A3B2E67E0AE4FA5DC0` 및 제시한 R11 runtime 호출 경로를 정적으로 대조했다.

**판정: P0 0건, P1 3건 유지.** 제안은 세 P1의 일부 실행경계와 기존 소스의 제한을 더 구체화하지만 권한·실행 결과·C4 승인이 아니다. Play610은 pending이고 C3 전체 선행 수용 및 C4 Review 상태도 유지된다.

Router의 `FixedUpdate`/`CommitNextFrame`, `Accept`, mode·map 전환 및 frame/receipt getter가 reset terminal·cohort closure·capture suppression을 확인한다. 이들은 Router 소유 입력/semantic frame을 보호한다. Adapter의 `TryTakeNotification`은 Adapter 내 notification을 거르지만 Hub latch의 cached state는 별도 확인 대상이다. Q-B `LateUpdate`/`TryTakeRequest`는 자체 상태와 retained request를 보고 Q-A presenter는 자체 confirmation-closed/state를 본다. C3 실제 `CommitForExecution`은 Q-B와 Presenter를 닫고 owner state를 `ExecutionCommitted`로 전환한 다음 lower completion을 수행한다. 따라서 C4 가드만으로 이미 상위에 retained/cached된 객체가 모두 차단됐다고 주장할 수 없다. 제안이 C3 실제 close와 새 lower admission을 결합하라고 한 것은 맞으며, old retained history를 지우거나 없는 publisher를 만들어 검증하지 말아야 한다.

저장 범위도 적절히 구분된다. 확인한 runtime 호출 범위에서는 활성 HubUI 세션에서 `ProfileAtomicSaveServiceV1.Save`를 직접 부르는 owned publisher가 확인되지 않았다는 관찰이다. `ProfileLaunchPreparationCoordinatorV1`의 `SaveUnderHeldRoot`/recovery-save는 launch 준비 중 실제 root lease 하 경로이며 현재 메뉴의 ordinary-save 권한으로 보면 안 된다. 공개 Profile `Save`는 Adapter/Router 상태를 읽지 않고 root lease와 durable reset barrier를 검사한다. 그러므로 C4 세션 가드가 이를 직접 차단한다고 주장할 수 없으며, 외부 프로세스나 독립 Profile writer 전체를 관리 latch 의무로 확대해서도 안 된다. 동시에 해당 조회 범위에서 미확인을 “owned HubUI publisher가 전혀 없다”는 포괄 증명으로 승격할 수 없다. 신규 owned publisher가 들어오면 그 실제 entry의 가드 결속을 따로 검수해야 한다.

스레드 후보는 Thread 객체 birth/issuer anchor가 실제 발급 이력에 없다는 점을 드러내고, unsupported wrong-thread 최초 호출을 payload 검증·Unity API 조회·소비 이전의 clean protocol rejection으로 한정한다. 이는 payload가 유효하거나 손상이 없음을 인증하지 않는다는 문구가 필요하며, C4 계약의 정상 Unity preflight 전체를 대체할 수 없다. 발급 스레드에서는 기존 전체 pair/root/generation·payload 검증과 손상 fail-closed 동작이 유지되어야 한다. 특히 잘못된 스레드에서 payload를 검사하지 않으면 그 시도 동안 reflected payload 손상을 탐지하거나 terminalize하지 않는다. 이는 clean pre-entry rejection의 비소비/비변경 규칙과 reflection corruption fail-closed 구분에 대한 명시적 규범 결정이 필요하다. birth/issuer anchor 불일치 자체를 일반 wrong-thread로 감추거나 재등록·복구해서는 안 된다.

기존 native FailStop을 worker에서 실행할 수 없다는 근거도 맞다. Adapter latch는 Router로 전달하고 Router fail-stop은 owned Unity actions의 Disable/RemoveCallbacks 및 lifecycle 작업을 수행한다. 따라서 worker 호출은 Unity 접근 금지 조건과 맞지 않는다. 제안의 alternative는 worker에서 authority 소비 없이 반환하고, 실제 native cleanup 완료라고 기록하지 않는 bounded entry rejection이다. 원래 Unity thread에서 fault를 확인한 경우에는 관리 fault 사건을 먼저 원본 pair 이력에 남기고 native cleanup으로 진행하자는 후보지만, 사건 등록 실패/부분 등록 예외, 손상 anchor, gate 경쟁, Unity thread 복귀 전에 writer가 들어오는 경우의 containment는 아직 충분히 증명되지 않았다. “그 시점의 특정 C4 entry를 막는다”와 “모든 producer/writer가 차단됐다”를 구별해야 한다. 독립 Profile writer는 durable lease/barrier 경계이며 session latch를 소비하지 않는다.

최소 후속 규범 결정은 (1) wrong-thread clean rejection이 payload 무검증을 허용하는 정확한 조건과 authority 인정 부재, (2) 발급 thread에서 관찰된 손상 및 anchor 불일치의 terminal/nativity 정책, (3) actual Q-A/Q-B retained closure와 신규 Router/Adapter guard admission의 책임 분리, (4) 실제 owned producer 부재 주장의 검색 범위, (5) fault 사건 기록과 worker/native cleanup 사이의 실패 처리다. 이 결정을 기존 REQ/AC 범위에서 해결할 수 있는지, 정확 amendment가 필요한지 승인 전에 고정해야 한다. A/B/C 자동 폐쇄나 모든 외부 writer 차단으로 확대할 근거는 없다.

R11 source/QA 고정 자료는 C4 신규 파일과 thread/writer 상태를 포함하지 않는다. C4 변경이 승인되면 현재 C3 큐·884개 입력 목록·R11 manifest를 C4 검증에 그대로 재사용할 수 없다. 이전 240/15/562/51/610의 이름과 결과는 역사로 보존하되, 새 source/meta를 포함한 별도 final manifest, C4 exact focused/필수 선택, 원장과 QA protocol이 필요하다. 이번 검토에서는 Git·네트워크·Unity·컴파일·QA·소스 변경을 하지 않았으며 실행 가능성이나 C4 acceptance를 발급하지 않는다.
