# C3 초기 게시 바이트 근거 원장 독립 검수

2026-09-29. 실제 독립 검수자 `gpt-6-luna`. 검토는 원장과 연결된 현재 파일·근거 문서의 읽기 및 SHA/줄 대조에 한정한다. Unity·컴파일·Git·네트워크를 실행하거나 기존 원장·코드·자산·설정·캡처·증거를 수정하지 않았다. 후보 바이트 승인이나 게시 승인이 아니다.

대상 `artifacts/c3-initial-code-publication-byte-evidence.json`의 SHA-256은 `A08FC892E7F0A7F90393863E8276BDC847287BB65CD5982299E9BB5EF997531C`이고, 참조한 후보 JSON의 현재 SHA-256 `A08A87B89CD4058D7B357F5FB6C8E7F30BEC863365526FC6BEAD40E0C1B57E5C`도 원장 선언과 일치한다.

## 대조 결과

- 후보 489개는 61개 exact-evidence 경로와 428개 direct-evidence gap 경로로 서로 겹치지 않게 분리되며, 합집합은 489개다. 61개 경로 중 60개는 과거 한정 실제 수용 지문 또는 정확 바이트 승인 근거이고, 1개는 R6 meta의 제한 정적 검수만 있다. 중첩 근거 행은 총 63개다. 요청된 60/1/428 집계와 일치한다.
- 61개 경로의 현재 파일 SHA는 원장 `CurrentSHA256`, 후보 JSON SHA와 실제 파일 재계산이 모두 일치했다. 63개 근거 행마다 근거 문서 현재 SHA·지정 줄의 현재 SHA 표기를 대조했고 모두 일치했다. 정확 파일 식별과 SHA가 같은 줄에 있거나, 명시된 별도 `FileIdentityLine`과 `EvidenceLine` 쌍에 있다.
- 근거 행 분류는 과거 한정 실제 지문 55행, 승인 규범이 정확 파일/meta 바이트를 고정한 행 6개, 정확 후속 소스 SHA 승인 1행, R6 meta 제한 정적 검수 1행이다. 이는 60개 경로의 근거를 제공하지만, 규범상 정확 바이트 허용을 실제 Unity 수용으로 바꾸어 읽지 않는다. 원장과 하위 근거 모두 `PublicationApproved=false`; C3 전체 수용도 false로 유지한다.
- Q-A `final-manifest.json` 현재 파일 SHA `B27EE836EF92AB1205D93B449331CD24A4B597383ED4C3A36D60FAC7EC02DABF`는 기존 Luna 문서가 당시 고정한 SHA `DEB56250A07CC469B71325D38C9B1E9232F68099ED7190924007F6C6E3492B19`와 다르다. 원장은 현재표를 과거 수용 사슬에 자동 연결하지 않고 제외했다. 역사 문서 및 현재 manifest의 각각의 실제 SHA와 역사 행을 확인했다.
- R6 측면 기록은 14개 manifest 파일 모두 현재 파일과 해시가 맞으며, 전부 제한 정적 상태·전체 C3 미수용으로 남는다. 원장은 R6의 Unity 재실행이나 최종 수용 결과를 조회했다고 주장하지 않는다. `NoExecutionPerformed=true`도 유지된다.

## 발견한 근거 포인터 공백

**P0 0건, P1 1건(원장 메타데이터 포인터).** `DesktopProfileLaunchAdapterV1.cs`의 정확 후속 SHA 승인 행은 해당 승인 문서의 7행 파일 경로와 8행 SHA가 정확히 일치한다. 다만 JSON의 `StatusAnchorLines`에 든 17행은 실제 16행 문서의 범위를 벗어난다. 승인 기록 자체나 파일/SHA 연결이 잘못된 것은 아니지만, 원장을 완전한 줄 단위 감사 원장으로 사용하기 전에 기존 버전을 보존하고 이 status-anchor 포인터만 정정한 새 원장이 필요하다. 이 점은 63개 SHA 근거 행 중 불일치 0건과 별도의 문서 인덱스 오류다.

따라서 60/1/428 집계 및 정확 바이트 대응은 정적 대조에서 일치하지만, 1개의 보조 status-anchor 위치는 보정 대상이다. 이 검수는 489개 전체 후보 파일을 재해시하지 않았고, 428개를 승인으로 해석하지 않는다. R6 실행·전체 C3 실행/수용, 초기 게시 allowlist의 승인, 깨끗한 복제 재현과 원격 상태는 확인하지 않았다. 기존 초기 게시 검수 기록 및 실패·역사 자료는 변경하지 않았다.

## 후속: R2 포인터 보정 확인

원본 원장 SHA `A08FC892E7F0A7F90393863E8276BDC847287BB65CD5982299E9BB5EF997531C`는 이력으로 보존한다. 후속 `artifacts/c3-initial-code-publication-byte-evidence-r2.json` SHA `5AF563201A0FB6344D15D91F8D6071933B4D765C2EF6BB3B49682F0BE0A67429`와 줄 단위 비교 결과 차이는 승인 문서의 범위를 벗어나던 `StatusAnchorLines` 한 항목을 17에서 16으로 바꾼 것뿐이다. 승인 문서는 실제 16줄이며 5행에 정확 소스 승인 범위, 7행에 파일 경로, 8행에 원장 현재 SHA, 16행에 C3 전체 수용이 아니라는 경계를 명시한다.

R2에서 61개 경로와 63개 근거 행의 현재 파일/문서 SHA 및 증거 줄을 다시 대조했고 status-anchor 범위 오류는 0건이다. **R2 포인터 결함 검수는 P0 0건, P1 0건으로 닫는다.** 이 폐쇄는 원본의 역사적 P1 기록을 삭제하지 않으며 60개 정확 근거 경로·1개 R6 제한 정적 경로·428개 직접 근거 공백의 집계를 바꾸지 않는다. 428개 공백, 초기 게시 검수의 5개 차단 묶음, R6의 진행 중 Unity 검증, 파일 게시 권한 미확정은 그대로다. 원장 정합성 보정은 게시 승인이나 실제 QA 통과를 의미하지 않는다.
