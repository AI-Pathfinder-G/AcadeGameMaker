## Bounded outcome

One generated-wrapper subscriber and InputMode owner publishes real device input to the explicit Movement/Transfer/Ordan Combat graph at -210, before its existing fixed phases. This is not an automatic Run/reward/choice/scene transition, authored playable-scene acceptance, physical controller certification or final menu/reticle art. The later camera owner supplies a value-only completed camera snapshot; absence of that owner is explicitly diagnosed, never replaced by a render Transform.

## Technical decisions already settled by Astra

- Keep Core AimSample unchanged: pending pointer coordinates are signed actual output pixels; AimSample coordinates are the approved normalized 1920x1080 grid. Negative/off-window actual coordinates must remain outside, not be prematurely clamped into a valid viewport.
- The signed/outside rule applies only to router-private pending actual coordinates. A published mouse AimSample always contains edge-clamped normalized screenPixel in 0..1919/0..1079; an outside pointer retains IsPointerInsideGameplayRect=false. Signed actual coordinates are never passed into the Core AimSample constructor.
- Convert actual pixels at -210 using exact completed camera framing. Inside is inclusive at left/bottom and exclusive at right/top; nearest pixel edge is rect origin through origin+size-1. Normalize with checked rational AwayFromZero as SYSTEM specifies; reuse TransferFixedMath.InverseGridToWorld rather than a second projection implementation. Fixed ortho 10000, rotation 0.
- Camera publication remains Q100. A future camera may hold exact pixel18 state and publish Round(pixel18*100/18, AwayFromZero), preserving the existing approved precision boundary. No Core ABI expansion.
- Movement initial Snapshot.Tick equals firstTick, not firstTick-1. Therefore initial device frame cannot claim completed prior player pose. Do not relabel a seed or alter Movement. Aim-dependent publication starts only after the first genuinely completed movement/camera pair; initial Movement and nullable-aim Transfer remain possible.
- Button actions retain initialStateCheck=false. Mode transition clears old edges before disabling/enabling maps; a held-through-lock button does not synthesize a new press. A real release and fresh press after enable is allowed through normal callbacks. No extra raw-event listener or held-control quarantine is currently justified. Current held Move may resume via a fresh Value callback; do not invent a neutral-before-resume rule.
- Gamepad aim uses the exact bound right StickControl's unprocessed value. Threshold is raw magnitude squared >=0.04; invalid/neutral stick retains last valid direction within the current mode epoch. No global Input System deadzone changes.
- Button edge callbacks buffer only; performed+canceled within a render interval retains the press and appropriate JumpReleased edge. Coalesce at most one of each semantic press per fixed tick. Frozen input is cleared only after the trio candidate commit succeeds. Gameplay state is never changed from a device callback.
- GameplayEnabled enables Gameplay only; UIOnly enables UI only; Cutscene/Transition/Ended enable neither. Default is Transition unless authoring explicitly enables Gameplay. Ended is terminal for this owner instance. Mode publication happens after all three candidate commits, with callback capture suppressed during map switching so cancellation cannot regenerate a batch.
- Transfer without valid aim may publish TransferPressed(null,tick), preserving active manual recall and inactive InvalidTarget. BasicAttack requires a valid current sample. Mouse-origin Transfer/Attack outside the gameplay rect are suppressed even for active recall. Missing camera cannot establish mouse-inside status, so mouse presses are suppressed; a gamepad Transfer press needs no pointer containment and can retain nullable-aim semantics.
- Device/scheme display events do not generate gameplay presses or change mode. Direct callbacks require the bound action, current permitted map and live enabled device; no legacy Input Manager, PlayerInput.SendMessage, synthetic input, virtual mouse or independently controlled action map.

## Planned seams and ownership

Create a narrow Input.Unity assembly depending on generated Input, Core, Movement/Movement.Unity, Transfer/Transfer.Unity and Combat/Combat.Unity. Grant only named Input.Unity and its test assembly friend access to needed internal consumers; do not relocate global input authority into Combat. Exact serialized graph references are mandatory, with no FindObject/static fallback. Initialization must occur after the graph's authored Awake preparation, and must validate all gate-owner registrations before changing any of them.

The coordinator freezes one exact tick frame, prepares all three candidates, validates all three, commits all three synchronously without callbacks, then publishes mode/map/batch consumption. Existing maintenance/damage merge and terminal future-key rejection are consumer-owned. No future input keys are created by InputRouter.

An explicitly bound camera provider must identify the same player and return only a completed camera pose. Actual player pose is read from Movement, not supplied by a different mockable gameplay owner. Tests may provide a frozen camera fixture, but cannot use it to relabel Movement's seed as completed state.

## Frozen coordination barrier

Add engine-free Core `InputFrameCommitReceipt` (readonly tick, nonnegative signed-64 frame ordinal, nonnegative signed-64 mode epoch, InputMode) and `IInputFrameCommitSource` with getter-only nullable CurrentReceipt and getter-only IsFaulted. IsFaulted is a monotonic false-to-true latch for this source instance; no reset is provided. The five named InputMode values are defined once in Core. Receipt equality is exact field equality. Consumer registration additionally freezes the actual source reference, which must be the same object as its gate owner; value equality never substitutes for source identity. The interface implementation is the single router. Existing Core DTOs are unchanged.

Coordination is explicitly opt-in. Existing gate-only fixtures/graphs retain every M5B1/M5B2/M5B4 behavior. New read-only registration checks validate all owner/source identities, already-created Movement motor, initialized Transfer and prepared/registered Combat, and exact unconsumed shared tick before any registration mutation. Same identity repeats are no-ops; a different identity rejects. Transfer may expose a normally named InitializeForInputRouter adapter to its existing validated initialization, used before the registration transaction, never inside read-only preflight. Failed graph initialization does not claim an atomic registry rollback; no coordinated registration, map enabling or frame receipt may be published in that case. Once all preflights succeed, durable registration proceeds Movement, Transfer, Combat synchronously without callbacks. No release/reassignment/rebootstrap API is part of this unit.

At each -210 frame freeze exactly one immutable receipt value before candidate preparation. First frame ordinal and mode epoch are zero; each subsequent successful frame advances ordinal by one. A real mode change advances epoch by one; unchanged mode retains it. Initialization adopts the explicit authored initial mode as epoch zero. Every counter successor is checked before any state mutation; no wrap, timestamps, device IDs, instance IDs or render-frame IDs.

Extend the candidate API with an overload carrying this receipt. Existing overloads retain uncoordinated behavior; when opted in they cannot bypass the mandatory receipt. Each candidate stages its consumer-local pending key, resulting gate and complete input queue. The key must match exact tick, next ordinal/epoch, registered owner and resulting lock state. Prepare all candidates in Movement, Transfer, Combat order; validate all; commit in the same order. The receipt value is unchanged throughout. Local commits do not publish global success.

The proposed candidate receipt and globally published CurrentReceipt are deliberately different stages. Candidate Prepare/Validate/Commit checks the proposed key against registered source identity, expected tick/sequence, candidate generation and gate; it must NOT require that proposed key equal CurrentReceipt yet. Only the downstream simulation phase checks local pending key against the newly published CurrentReceipt. During first bootstrap CurrentReceipt is null: all three valid ordinal-zero candidates may prepare/commit against initialized expected ticks; global ordinal-zero publication then permits their first phases. Before that final publication, every phase rejects the absent proof, including an otherwise empty bootstrap frame.

Only after all local commits succeed, perform exclusive map switching under callback suppression (disable previous map before enabling the selected one; never both). Then assign effective mode/epoch, consume the frozen callback batch and input-ID reservations, and publish CurrentReceipt as the final authoritative assignment. There is no fallible work/callback between these final value assignments. CurrentReceipt stays at its previous value throughout local commits and map changes. Same-mode frames do not unnecessarily disable/re-enable their map.

At the first line of each opted-in phase, before attempt latches, queue consumption, physics, motor/session changes or publication, require an unconsumed local pending key equal to the exact source object's CurrentReceipt and exact phase tick. Ordinal must be the next one for this consumer; mode epoch stays or increments exactly once and the local lock must match its mode. Missing/stale/future/already-consumed/mismatched proof rejects without any phase mutation. Receipt consumption occurs at the existing consume-on-attempt boundary, not after successful simulation; this does not promise rollback of later domain failures. Empty frames require receipts too, including the initial bootstrap frame.

Before even comparing receipt values, the phase rejects source.IsFaulted or its own terminal-closed coordinated lane. Thus retaining an old CurrentReceipt during faults can never authorize a still-pending older phase. Combat terminal close clears its pending key and permanently marks that coordinated lane closed; later Combat phase calls reject even if explicitly invoked on the disabled component. Remaining Movement/Transfer lanes are not retired by Combat's closure.

An ordinary pre-commit preparation/validation failure leaves all consumers, effective mode/maps, IDs, CurrentReceipt and frozen callback batch unchanged. No downstream phase can advance without the new global proof. Retrying the same tick is allowed once the rejected dependency is explicitly corrected. Unexpected failure after the first local commit or during map switching latches the router Faulted, preserves the old global receipt and unconsumed frozen batch, and forbids further commits/mode publications/ID advancement. Best-effort map disabling is permitted solely to suppress further callbacks; actual map enabled bits and failing stage are retained diagnostically, not described as rollback. No partial state is automatically repaired or rebootstrap invented. Since the global proof remains old, even an earlier locally committed consumer cannot advance. Tests inject each such boundary using internal test-only fault seams with no production side effect by default.

OnDisable unsubscribes and disables maps under capture suppression. If initialization had completed, it enters Faulted and freezes publication rather than silently unlocking or resuming. OnDestroy disposes the wrapper. Re-enabling an initialized disabled/faulted instance is rejected; a future explicit replacement-owner lifecycle requires its own contract.

## Callback ordering, modes and diagnostics

Accepted Point and qualifying raw Aim events receive checked monotonically increasing callback ordinals; the last accepted ordinal selects the active aim source. This is the finite Input System callback order, not event timestamps or device display state. Mode changes discard old source/edge records and start a fresh callback epoch. Raw stick below threshold does not replace direction or steal aim ownership. Every committed tick with valid retained or refreshed aim publishes an exact-current-tick AimSample with the next sample ID: threshold governs direction updates, not the required re-publication of retained intent with current sampleTick. The same sample value/ID is sent to Transfer and Combat. Publication IDs advance only at successful global frame publication. BasicAttack sequence IDs advance only for actual committed valid attacks. Failed frames, diagnostics and suppressed presses consume no publication IDs.

Mouse origin is Movement's completed position converted through the existing Q4096ToQ1000 helper. Reuse TransferFixedMath HasMouseDirection/NormalizeMouseDirectionQ4096, including its approved 0.05u boundary; no new facing fallback. Raw stick normalization uses finite double arithmetic, Math.Sqrt and AwayFromZero component rounding/clamp after the exact raw threshold test. Signed actual mouse pixels use finite checked AwayFromZero conversion to int; overflow rejects before pending-state mutation. A valid camera requires exact prior tick, same bound player, supported centered viewport and the existing fixed camera validation. Absent/not-yet-completed camera is BootstrapPending or CameraUnavailable; stale/wrong-player/invalid framing is CameraRejected. These omit the camera/aim pair, preserve Movement, suppress mouse attack/transfer and all basic attacks, and allow only gamepad nullable-aim Transfer. They do not fabricate a completed pose.

The mode request authority is one explicitly registered requester object. Requests require a defined mode, nonempty reason and exact next unprocessed player tick. One request may be pending per tick; identical replay is a no-op and conflict rejects unchanged. Ended cannot transition back. Actual Run, Choice or scene consumers are not invented. Pause, UI Navigate/Point/Click/Scroll/Submit/Cancel, ChoiceSkill and Interact currently produce only bounded diagnostic bits for that frame, not gameplay effects or queued future commands. Pause screen/clock implementation is a subsequent Approved unit; this limitation must be stated in evidence. Unbound action flags and camera disposition live in one immutable last-frame diagnostic plus a fixed fault-stage enum, never an unbounded event list or log-per-callback. No gameplay command ID is allocated to diagnostics.

## Terminal boundary

### Bootstrap mode clarification — Astra Approved, Luna consistency review PASS, 2026-09-08

Before CurrentReceipt has its first value, RequestMode may accept only the already adopted initial mode (normal exact-tick requester/replay checks still apply). A different mode rejects unchanged as BootstrapRequired; it must not occupy the pending-request slot. Thus the initial committed receipt always has the authored initial mode and epoch zero. After this receipt, ordinary next-unprocessed-tick mode requests may change modes and increment the epoch. This resolves the initial-proof/epoch sequencing ambiguity without changing product controls or permitting an impossible pending request. AC-M5B5-002/008 includes rejected pre-first different-mode request, unchanged state, same-mode idempotence and subsequent successful mode transition.

The authored owner must request a locked mode before terminal cleanup. If a completed boss-death publication exists and the proposed frame is still GameplayEnabled, reject with TransitionRequired before any commit rather than fabricating Run success or injecting new terminal attacks. InputRouter does not claim M5A/Run binding in this unit.

At cleanup d+1 the router still coordinates all three consumers in a locked frame. Transfer consumes its proof at -200. Existing terminal discard at -195 must validate global/local Combat proof and close that pending proof in the same prevalidated discard transaction before disabling Combat; it must not advance Combat or relax exact empty/future-key/damage rejection. Movement consumes normally. A narrow read-only MatchesRetiredInputGraph on the explicitly bound teardown verifies its completed immutable receipt, exact player/Transfer/Combat references, disabled Combat, post-cleanup player tick and locked gate. Only this evidence permits the router to latch CombatRetired and omit Combat from later frames. No loose disabled-component test or inferred death alone counts. Remaining two consumers stay locked and require complete shared frame proofs; Gameplay re-entry is rejected until a separately approved replacement Combat lifecycle. This unit never automatically switches rooms, pays rewards or unfreezes retired Combat.
