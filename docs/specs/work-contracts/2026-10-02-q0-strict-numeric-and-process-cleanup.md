## 수정 전 실패 바이트 보존

기존 `preparation.json`, `negative-tests.json`, `preparation-v2.json`, `negative-tests-v2.json`, 테라 최초/v2 보고와 실패 소스 기록은 삭제·덮어쓰기·재생성하지 않는다. v2의 통과한 합성 관측은 역사로 보존하되 전체 준비 성공·운영 시작 근거로 수용하지 않는다.

## 정확 허용 변경

검증기는 준비·음성 결과의 **모든 중첩 숫자 필드** 목록과 의미를 명시하고 JSON 원시 종류가 Number이며 정수 토큰인지, 허용 범위·필수 기대값인지 순서대로 검사한다. 문자열/불리언/null·배열/객체·소수/지수 표기·범위 초과·음수/0이 금지된 필드의 해당 값·중복/미지 필드를 거절한다. `CandidateFileCount`, `InputObservations.ExitCode`, `DeadlineMs`만 고치고 나머지 숫자 필드를 암시 변환에 맡기지 않는다. 실제 시간처럼 소수형이 필요한 필드는 정수와 별도 숫자 형식/유한 범위를 명시하며 문자열을 허용하지 않는다. 필드별 정상 경계와 잘못된 JSON 종류·범위의 음성 시험을 표로 기록한다.

정리는 세션 닫기, 입력/reader 닫기, 모듈 제거, 시계 정지를 중첩 `try/finally`로 묶어 앞 단계 예외에도 뒤 단계가 시도되게 한다. 각 실패를 보존하고 성공으로 바꾸지 않는다. 운영 발급은 키를 소유한 **별도 전용 호스팅 프로세스**에서만 수행하며 성공/실패/기한초과 후 반드시 종료한다. 신뢰 주 조정자는 프로세스 핸들·PID·생성시각과 절대45분 단조 기한을 별도로 보유하고, 자발 종료가 정해진 제한 내 확인되지 않으면 그 정확 소유 프로세스만 종료한 뒤 실제 종료를 관측한다. 종료를 관측하지 못하면 발급 실패·미정이며 키가 폐기됐다고 기록하지 않는다. 개인키를 부모에 전달하지 않는다. 부모/다른 PowerShell/사용자 프로세스 종료는 금지한다.

원본 모듈의 예외를 의도적으로 고치거나 운영키로 실패를 유발하지 않는다. 시험용 닫기 단계 대역에서 첫/중간 정리 예외와 정리 지연을 주입하고, 다음 단계 시도·오류 보존·전용 자식 실제 종료·감시자의 제한 종료를 확인한다. 실제 오류 없는 합성 비영속 키 시험은 기존 승인 범위에서만 가능하며 운영키0을 유지한다. 프로세스 종료에 따른 핸들 수명 종료를 관리 코드 `Key.Dispose`의 성공으로 기록하지 않는다. 메모리 덤프/스왑까지 물리적 삭제됐다는 주장도 하지 않는다.

## v3 초안과 불변 최종의 정확 경로

증거 루트 `output/q0-external-authority-evidence-r1`에서 다음 네 경로만 추가 허용한다.

- 수정 가능한 `preparation-v3-draft.json`, `negative-tests-v3-draft.json`
- 최종 `preparation-v3.json`, `negative-tests-v3.json`

테라는 초안 두 개만 작성·수정하며 완성 전 미수용 작업물임을 명시한다. 전체/게시/루나 수용 플래그는 거짓이다. 초안은 최종 키 없는20소스SHA, 숫자 전수 검증 및 실제 열린 입력/EOF/정상·정리 예외/자식 종료 증거에 결속한다. 두 초안은 자기SHA나 서로의 미래SHA를 내부에 넣지 않는다. 최종 보고 경로는 `docs/verification/2026-10-02-q0-external-authority-terra-report-v3.md`, 루나 후속 보고는 `docs/verification/2026-10-02-q0-external-authority-luna-review-v3.md`다. 루나의 독립 시험은 기존 허용 격리 범위에서 수행하고 공개 결과를 보고에 기록한다. 불변 최종 파일을 먼저 만들지 않는다.

루나는 정확 초안 두SHA와 최종20소스를 검수하고 숫자형 음성·정리 예외/열린 입력 기한·실제 전용 프로세스 종료를 독립 재현한다. 아스트라가 두 P1의 한정 폐쇄를 판단한 뒤, 발급자는 초안SHA를 다시 대조하여 **재직렬화·상태필드 수정 없이 같은 원시 바이트**를 각각 최종 경로에 `CreateNew`로 한 번 복사한다. 각 최종SHA=검수초안SHA와 바이트 차이0을 확인한다. 그 뒤 초안도 수정하지 않는다. 일부 최종 생성 뒤 오류가 나도 지우거나 덮어쓰지 말고 상태를 보고한다.

## 계획 결속과 비순환 순서

스키마/검증기의 `CurrentPreparationEvidence`는 기존 정확2행 `Role/Path/Sha256` 구조를 유지하되 승인 경로를 **v3 최종 두 파일**로 전환한다. 운영에서 v1/v2/초안 경로 선택은 거절한다. 실제 v3 SHA는 계획 작성 때 원시 파일에서 계산하며 소스/스키마에 미래SHA를 넣지 않는다. 합성 검수는 메모리 또는 별도 시험 경계에서 초안 바이트를 검사할 수 있으나 운영 검증기에 초안 선택·검사 생략 스위치를 추가하지 않는다.

최종 키 없는20소스→v3 초안 시험/루나/아스트라→동일 바이트 최종 두 개→공개키 지정 자리 대입/정확 전이검증→source-freeze→실제 계획의 두 v3 SHA→서명 순서를 유지한다. 기존 준비 결속 계약의19개 동일·검증기 지정 공개 자리 전이 규칙은 그대로다. 실제 최종SHA를 알기 전에 issuer에 v3SHA를 삽입하지 않는다. v3 발급 뒤 소스가 바뀌면 기존 최종을 덮어써 맞추지 않는다.

이 계약의 실제 참여는 아스트라 문서 판단이며 테라 구현·루나 검증 결과를 소급 주장하지 않는다. 원래 원격 두 문서/가지·미실행 계획·기존 계약SHA·원래 Git·원문534를 유지한다. 새 계약/증거를 원격 게시 범위에 자동 추가하지 않는다. 인간의 새 결정은 필요하지 않다.
