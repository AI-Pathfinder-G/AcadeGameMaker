## API의 문서상 보장과 남은 불확실성

REQ-R01COMPTIME-002. Microsoft는 `Direct3D11CaptureFrame.SystemRelativeTime`을 합성기가 그 프레임을 렌더링한 QPC 시각으로 정의하고 `TimeSpan`을 100나노초 단위로 정의한다. 현재 코드는 실제 프레임을 얻고 크기를 확인한 뒤 `frame.SystemRelativeTime().count()`를 읽고 다음 초기화자에서 `qpc()`를 호출한다. 그 뒤 원시를 출력하고 저장한 수신 시각으로 원래 가드를 검사한다. 로그 출력 뒤 시각을 수신 시각으로 바꾸어 재검사하지 않는다.

현재 변환은 정수 몫·나머지로 `ticks * 10000000 / frequency`를 안전하게 계산한다. 실제 빈도10000000에서 결과는 원래 ticks와 정확히 같으므로 이 사례의 56346 차이는 배율·반올림으로 설명되지 않는다. 다른 시계나 UTC를 프레임 시간과 혼합한 코드도 이 구간에는 없다.

공식 QPC 문서는 프로세서·스레드 간 일관성과 서로 다른 스레드 측정의 ±1틱 순서 불확실성을 설명한다. 이번 차이는 56346틱이므로 그 ±1틱 설명을 허용오차로 확대할 수 없다. 플랫폼 이상·API 구현 이상·가상화·그래픽 경로 등 특정 원인은 현재 증거로 확정하지 않는다.

이번 공식 문서 판독에서는 **해당 프레임 시간이 `TryGetNextFrame` 반환 뒤 임의의 소비자 QPC보다 항상 작거나 같다는 별도 명시 보장, 허용 미래 편차, 미래 프레임 대기 규칙을 확인하지 못했다.** 이는 미래 프레임 허용을 공식 API가 보장한다는 결론도 아니다. 문서의 의미 정의, 현재 프로그램이 요구한 강한 부등식, 실제 한 사례의 불일치를 구분한다. 합성기의 예정 표시 시각·특정 화면 주사율 때문이라는 설명도 이 조사에서 확인되지 않아 사실로 쓰지 않는다.

AC-R01COMPTIME-002. 원래 부등식을 공식 문서의 직접 인용으로 정당화하거나 반대로 문서에 없다는 이유로 폐기하지 않는다. ±1틱과 56346틱, 변환과 원시 시계, 호출·수신·합성 시각을 구분한다. 임의5/10/16밀리초 허용오차·드라이버 원인 확정·시각 보정은 0이다.

## 다음 최소 관측 제안

REQ-R01COMPTIME-003. 현재 근거만으로 수용 행동을 바꾸는 최소 수정은 제안하지 않는다. 다음 한정 후보는 **원래 가드를 유지한 호출별 최초 프레임 관측**이다. 승인된다면 기존 첫 프레임 한 줄에 아래 실제 시각·빈도·스레드 식별만 추가한다.

- `TryGetNextFrame` 호출 직전·반환 직후 QPC.
- `SystemRelativeTime` 접근 직전·직후 QPC.
- 기존 `receivedQpcTicks`, 기존 원시 구성 직전의 추가 QPC 한 번, 현재 스레드 식별자, 해당 프로세스에서 실제 재조회한 QPC 빈도.
- 기존 frameTime·origin·변환 상하한·StartCapture 전후·양방향 판정은 그대로 보존한다.

각 측정은 원래 같은 스레드에서 독립 문장으로 수행한다. 실제 프레임이 없는 폴링에는 원시를 추가하지 않고, 최초 실제 프레임에만 한 줄을 출력한다. 추가 QPC는 관측값일 뿐 기존 수신 상한을 대체하지 않는다. 후속 QPC가 프레임 시각을 따라잡았다는 이유로 원래 거절을 통과시키지 않는다. 기다림·재시도·프레임 폐기·캡처 항목 재생성·고정 지연·스레드 affinity/우선순위 변경·시간 오프셋·하한/상한 삭제·시각 합성은 0이다.

이 관측은 API 호출의 어느 경계에서 미래 차이가 보이는지, 실제 빈도·스레드·변환 일치 여부를 좁힌다. 원시가 계속 미래라면 그 사실과 실패를 보존하며 여러 번 재현해 평균 허용치를 만들지 않는다. 위 추가 관측만으로 플랫폼 원인까지 확정하거나 수용 계약을 자동 변경하지 않는다.

AC-R01COMPTIME-003. 정적 판독은 추가 관측이 최초 프레임 한 번이며 원래 가드와 최초 실패·단조성·계수 순서·30Hz 정책·기한을 보존하는지 확인한다. 실제 실행에서 추가 값의 부재·관측 실패·원래 시간 거절은 각각 실제 결과로 남긴다. 정상 프레임이 있어도 정상 인코딩·파일·정리·독립 수용 전에는 제품 성공으로 처리하지 않는다.

## 대안 검토: 같은 프레임의 실제 수용 시점 분리

REQ-R01COMPTIME-005. Root가 제안한 대안은 임의 허용오차 대신 최초 수신 원시를 보존하고, 같은 프레임 시각에 실제 QPC가 도달한 시점을 별도 수용 시각으로 삼는 것이다. 이는 공식 API가 미래 시각을 보장한다는 주장이 아니라 **프로그램의 수용 정책 변경 후보**다. 현 초안의 관측 전용 기본안과 함께 자동 구현하지 않는다. 아스트라는 기존 상한 요구와 AC 영향을 명시해 관측 전용 또는 아래 대안 중 하나를 선택·승인해야 한다. 한 실행에 두 예산을 합산하거나 실패 후 대안으로 자동 전환하지 않는다.

대안을 승인한다면 수신 직후의 실제 QPC와 원래 frameTime을 모두 보존하고, 사례 원점 하한·단조성·창/원래 신원·크기 조건은 유지한다. 상한을 넘는 프레임은 즉시 제출하지 않고 같은 프레임 객체 최대1개만 보류한다. 현재 실제 QPC의 100나노초 변환이 해당 frameTime에 도달한 경우에만 별도 `acceptedQpcTicks`와 실제 지연을 기록하고 인코딩 경로로 진행한다. frameTime 변경·수신 시각 덮어쓰기·추정 오프셋·가짜 프레임·무조건 폐기는 0이다. 이미 수신 상한 안인 프레임에는 추가 대기를 넣지 않는다.

보류는 기존 captureDeadline 및 전체/사례 절대기한의 최소 경계 안에서만 허용하며 종료/회수 예비시간을 소비하지 않는다. 도달 목표가 기존 captureDeadline 이상이면 즉시 첫 실패다. 같은 스레드의 짧은 유한 간격 점검마다 원래 stopEvent·Unity/Root 생존·캡처 항목 Closed·창/스레드 정체성과 실제 QPC를 확인한다. 그 동안 새 프레임을 꺼내거나 큐에 쌓지 않는다. 별도 무기한 Wait·새 스레드·항목 재생성·추가 프로세스는 0이다. Root 관리자는 기존 비차단 입력 감독과 원래 Job 정리를 계속한다.

메모리 범위는 기존 풀 버퍼2와 보류 프레임 참조 최대1로 닫고 추가 CPU/GPU 복제·보류 배열은 0이다. 실제 표면의 허용 크기/형식과 기존 frame byte 상한을 확인하는 위치도 승인 설계에서 닫아야 한다. 이 객체 수 제한을 그래픽 드라이버 내부의 전체 메모리 상한 입증으로 확대하지 않는다. STOP/Closed/기한/원래 신원 불일치면 보류를 실패로 종료하고 같은 프레임을 해제한 뒤 기존 정리 순서로 끝낸다.

이 대안은 기존 `frameTime<=qpc_100ns(receivedTicks)`의 즉시 거절 의미를 `수신 원시 보존 + frameTime<=실제 acceptedQpc`로 바꾸므로, 가드를 몰래 삭제하는 변경으로 구현할 수 없다. 원래 REQ/AC의 시간 결속·첫 실패·프레임 계수/인코딩 시각·단회 수용 기준을 한 호환 조항에서 먼저 개정해야 한다. 기존 기한 내 도달은 시계 이상 부재나 API 정상 동작의 증명이 아니다. 실제 기다림·도달·미도달을 각각 원시로 판독한다.

AC-R01COMPTIME-005. 대안을 선택한 승인에는 위 정책 차이·정확 신원/stop/기한 점검·보류 객체 수·실제 수용 시각 필드·실패 시 프레임 해제와 검사 계획을 고정한다. 독립 판독은 즉시수용·보류후수용·목표기한밖·stop/Closed·정리 실패 경로를 정적으로 확인한다. 발생하지 않은 분기는 동적 미관측으로 남기고 새 유발 시험 예산을 만들지 않는다. 승인 없는 구현·대기·추가 실행은 0이다.
