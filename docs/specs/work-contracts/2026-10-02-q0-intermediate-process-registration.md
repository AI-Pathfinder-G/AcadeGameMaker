## 실제 구조와 허용 변경

준비 복제의 큐 `C4-QueueChild`는 선택 실행자를 별도 프로세스로 생성하고, 선택 실행자 `C4-StartChild`는 QA를 별도 프로세스로 생성한다. QA가 Unity를 시작한다. 사후 OS 계보 연속성만으로 직접 생성 시 보유한 핸들을 입증할 수 없으므로 단일 직접 QA 합성 결과를 이 사슬의 성공으로 수용하지 않는다.

broker는 기존 `artifacts/c4-canonical-final-validation-queue.ps1` 프로세스에 둔다. 같은 프로세스의 lease 상태·채널 처리와 큐를 결합하되 선택 실행자와 QA 프로세스를 합치지 않는다. 변경은 준비 복제 `output/q0-trusted-child-r1` 안 기존 승인 큐·선택 실행자·후속 QA·lease/selftest·실행 schema/verifier와 기존 네 C#의 해당 등록 호출에만 허용한다. 다른 소스·조립·환경변수·메시지 종류는 추가하지 않는다.

## 역할과 생성 경로

메시지 종류는 `StartSlot`, `RegisterLauncher`, `RegisterEditor`, `AuthRequest` 그대로다. `Role`은 생성 대상이며 `StartSlot`/`RegisterLauncher`에만 `SelectedRunner`, `QA`를 추가한다. 허용 직접 생성 관계는 큐/broker→SelectedRunner→QA→Unity, 등록된 Unity→Verifier다. `RegisterEditor`는 기존 Unity 편집기 부착에만, `AuthRequest`는 Unity/Verifier에만 허용한다. 중간 역할에는 도전값과 권위 객체를 주지 않는다.

1. 서명 부모는 큐/broker의 실제 신원이다. 기존 수동 인증·서명/파일 검증·실행 소비 관문을 통과한 뒤 큐는 같은 상태기계의 내부 호출로 정확 Stem의 SelectedRunner 시작 슬롯을 예약한다. 자체 파이프에 연결하여 교착하지 않는다. 실제 생성 호출에서 반환된 핸들로 직접 등록한 뒤에만 그 runner가 다음 단계를 예약할 수 있다.
2. 등록된 runner는 실제 파이프 피어로 QA `StartSlot`을 요청한다. broker는 이미 등록된 runner 신원·Stem·부모 수명·정확 소스/인자를 확인한다. runner는 허용 슬롯에서 한 번 QA를 생성하고 반환 핸들을 유지하며 `RegisterLauncher`를 전송한다. broker의 등록 완료 응답 뒤에만 정상 실행 관측으로 진행한다.
3. QA는 등록 완료 후 기존 Unity 슬롯·시작자/편집기 등록을 수행한다. QA가 먼저 연결하면 미등록 부모의 시작 요청은 같은 순번과 고정 총기한 안에서 `PendingRetry`만 반환하며 SlotId는 빈 값, Challenge/Authority는 null이다. 슬롯 예약이나 하위 생성은 아직 허용하지 않는다. 등록 완료 후 실제 피어를 다시 확인한다. 선행 생성자와 같은 연결을 붙잡아 등록을 막지 않는다.
4. 각 단계의 SlotId는 broker가 생성하며 InvocationId·Stem·대상 역할·실제 직접 부모 PID/전체 ticks·시작 요청 순번에 결속한다. 중간 역할은 Stem마다 한 생성만 허용한다. Verifier의 반복 재검사는 기존 승인된 실제 Unity별 다중 슬롯으로 유지한다. 생성 실패·등록 실패의 슬롯을 비워 재사용하지 않는다.

## 생성자 핸들과 인자 결속

기존 등록 필드에 `CreatorHandleValue` 하나를 추가한다. 이는 생성자 프로세스 핸들 테이블의 실제 자식 핸들 값을 포인터 폭에 맞게 0 확장한 대문자 16자리 16진수 문자열이며 0은 거절한다. `RegisterLauncher` 및 Unity `RegisterEditor`에만 필수다. 숫자 자체는 권위가 아니다.

원격 생성자는 실제 생성 또는 승인된 편집기 부착에서 얻은 핸들을 응답 장벽까지 살아 있게 유지한다. broker는 실제 파이프 발신자의 검증된 프로세스 핸들에서 Windows `DuplicateHandle`로 그 핸들을 자신의 프로세스에 복제한다. 원본을 닫는 플래그는 금지한다. 복제 핸들이 실제 프로세스이며 살아 있는지, PID·전체 시작 ticks·경로가 등록값 및 독립 OS 조회와 같은지 확인한다. 직접 부모는 등록된 실제 생성자와 같아야 한다. 큐의 내부 등록은 실제 생성 호출 반환 핸들을 직접 사용하되 같은 검증을 적용한다. 핸들 복제 실패·권한 부족·닫힌 핸들·잘못된 객체 유형은 즉시 실패다. 핸들 값만 저장하거나 `GetProcessById`의 사후 결과로 대체하지 않는다.

Unity 시작자와 편집기가 다르면 기존 DED9의 중간 시작자 핸들·실제 계보 규칙을 유지한다. QA에 사후 부착한 편집기 핸들이 있다는 사실을 QA가 직접 생성했다는 증거로 바꾸지 않는다. 중간 관계를 실제로 확인하지 못하면 실패한다. 프로세스 종료 시 핸들·슬롯·도전값을 폐기하되 신원과 소비 순번의 거절 이력은 실행 세대가 끝날 때까지 남긴다.

역할별 실행 경로·소스 경로/원시SHA·정확 인자 토큰은 서명 계획의 기존 실행 정의와 현재 소스 결속에서 결정한다. `StartSlot.ArgumentSha256`은 그 고정 토큰에서 계산한 값과 같아야 한다. broker는 실제 OS 명령행을 엄격하게 토큰화하여 전체 토큰·개수·순서와 별도로 대조한다. 호출자가 보낸 지문만 대조하지 않는다. 조회 실패나 모호한 인코딩은 실패다. 실제 계획SHA·동적 SlotId·도전값·순번을 사전 인자에 삽입하여 계획 자기참조를 만들지 않는다. 현재 복제의 역사적 `PlanSha256` 인자 호출은 그대로 운영 가능하다고 가정하지 않고 기존 허용 도구에서 고정 계획 경로의 직접 검증으로 연결한다.

## 처리 수명과 검증 관문

큐는 runner 종료를 기다리는 동안에도 파이프 등록과 인증 요청을 처리해야 한다. 기존 무조건 대기 반복으로 채널을 막지 않는다. 같은 프로세스의 비동기 대기/사건 처리로 구현하며 모든 broker 상태 전이는 한 직렬화 경계에서 처리한다. 자식 출력도 계속 배출한다. 각 요청의 재접속은 최초 단조 총기한을 공유하고 부모 죽음·기한 초과 시 하위 시작과 권위를 거절한다. 종료 대상은 실제 소유 핸들과 전체 ticks가 다시 일치하는 자식으로만 제한한다.

기존 자체시험과 `channel-tests.json`/테라·루나 보고 범위에서 실제 별도 runner→QA→합성 Unity 사슬, 빠른 QA 접속, 지연된 부모 등록, 교착 없는 정상 진행, 위조/닫힌/다른 객체 핸들, 다른 실제 발신자, 잘못된 직접 부모/전체 ticks/Stem/인자, 단계 생략·역순·중복, 부모 사망·시간초과·응답 손실을 검증한다. 순수 합성 객체 배열이나 직접 QA만의 결과는 이 검증을 대체하지 않는다. 실제 Unity 컴파일·편집기 계보와 독립 루나 검수는 기존 관문으로 남는다.

현재 소스와 요청/응답 예제를 이 보완에 맞춰 함께 고정한 뒤에만 네 C# 별도 담당의 편집을 승인할 수 있다. 기존 채널 합성 48개는 보고된 당시 범위이며 이 새 사슬을 증명하지 않는다. 본 승인 자체는 구현 성공·추가 P0/P1 폐쇄·전체 수용이 아니다.
